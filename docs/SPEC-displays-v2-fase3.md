# SPEC: Displays v2 · Fase 3 — Audio por perfil (Millennium Clipboard)
Al aplicar un perfil de monitores, cambiar TAMBIÉN la salida de audio por default de Windows (ej. el perfil "TV" manda el sonido a la TV).
- Estado: READY
- Fecha: 2026-07-24

## Por qué (el dolor)
Hoy un perfil de Displays v2 mueve monitores (posición, primario, resolución) pero NO toca el audio. El caso real: Guido tiene un perfil "TV" que enciende/reorganiza la pantalla de la TV, pero el sonido sigue saliendo por los parlantes del escritorio — hay que ir a mano al panel de Sonido de Windows cada vez. La Fase 3 cierra ese hueco: que el perfil sea el "botón único" de una configuración completa (video **+** audio).

## Contexto del código (del spike — nombres REALES, verificar líneas)

**Factibilidad (spike 2026-07-23, verificado adversarialmente):** SÍ es factible desde el backend Rust, reusando maquinaria que la app YA tiene. Ver "Riesgos" para la fragilidad.

- **Qué es un perfil hoy**: `Profile { name, layout: Layout { outputs: Vec<OutputConfig> } }` — crate vendorizado `monarch` (`src-tauri/vendor/monarch/src/model.rs:87`). Todo el perfil es **pura topología de video**; no hay ningún concepto de audio. `OutputConfig` (model.rs:44): display_id, enabled, position, resolution, refresh_rate_mhz, primary.
- **Dónde se guardan los perfiles**: root `AppConfig` (model.rs:128, con `#[serde(default)]` a nivel struct) serializado ENTERO a `%APPDATA%\com.guidocameraeq.millennium\displays.json` vía `MillenniumConfigStore` (escritura atómica, `src-tauri/src/displays/store.rs`). `AppConfig.profiles: Vec<Profile>` son los perfiles del usuario. **NO hay campo de versión/schema**: la compatibilidad hacia atrás es 100% por serde defaults.
- **Precedente CLAVE para dónde guardar el audio**: los **atajos por perfil** NO viven dentro de `Profile` — viven en `AppSettings` (model.rs:99, `#[serde(default)]` a nivel struct) como `profile_shortcuts: BTreeMap<String, String>` (nombre_de_perfil → accelerator). Es exactamente el patrón que corresponde para "metadata por perfil que no es topología de video": un mapa nombre→valor en `AppSettings`, keyed por nombre de perfil.
- **El comando que aplica un perfil (con red de auto-revert)**: `displays_load_profile` (lib.rs:1379, registrado en invoke_handler lib.rs:2205) → `cargar_perfil` (`src-tauri/src/displays/mod.rs:889`) → `apply_profile`/`apply_layout` del motor CCD → `aplicar_con_red(plazo)` (mod.rs:1112) que arma el watchdog de auto-revert.
- **La vía SIN red (commit inmediato)**: `aplicar_perfil_directo` (mod.rs:922) — la usan el **perfil de arranque** (lib.rs:2138, si `launched_hidden`) y los **atajos globales** de perfil (lib.rs:1276). Un perfil con audio también debe cambiar el audio por ACÁ.
- **El auto-revert (red de seguridad)**: `PendingConfirmation { previous_layout: Layout, ... }` (manager.rs:13) — hoy captura y restaura **SOLO topología de video**. `rollback_pending` (manager.rs:179) re-aplica el layout previo. La capa que orquesta cada apply/revert/evento "reverted" es `mod.rs` (`aplicar_con_red` 1112, `reportar_desenlace` 1165, `confirm` 694, `revert` 706) — es la capa Millennium (no el vendor monarch), y es el enganche natural para (a) aplicar el audio tras el video y (b) capturar/restaurar el audio previo en el rollback.
- **Migración existente (patrón a imitar)**: `MonarchDisplayManager::new` (manager.rs:53-113) ya hace "upgrade-on-load" idempotente sin número de versión (rellena defaults, siembra last_known_good, migra IDs por EDID); si algo cambió, reescribe displays.json. Es el lugar canónico si hiciera falta tocar datos al cargar.
- **La UI de perfiles (frontend)**: sub-pestaña PERFILES del panel Displays. El usuario SOLO tipea un **nombre** (`#displays-profile-name`, index.html:224); el backend captura el layout actual al guardar. Guardar/actualizar = `invoke('displays_save_profile', { name })` (main.js:2194, upsert por nombre). Listar = `displays_list_profiles` (main.js:2127); cargar = `displays_load_profile`; borrar = `displays_delete_profile`; atajos = `displays_set_profile_shortcut`/`displays_clear_profile_shortcut`. Cada item de la lista se pinta con `buildProfileItem` (main.js:2033: innerHTML estático + `setText`, nunca strings crudos del backend). **Cero referencias a audio en el frontend hoy** (los únicos hits de "audio/sound" son los FX de sonido de la UI).
- **El análogo visual para un selector**: el pane AJUSTES ya tiene un `<select class="displays-setting-select">` (el de "perfil de arranque", `updateStartupSelect` main.js:2373, estilos styles.css:3308) — mismo patrón para "elegir un dispositivo de una lista".
- **Maquinaria Win32/COM que YA existe**: el crate `windows` 0.60 está declarado bajo `[target.'cfg(target_os="windows")'.dependencies]` (Cargo.toml). El módulo displays YA hace COM real (`CoInitializeEx`/`CoCreateInstance`/`CoUninitialize` instanciando `IDesktopWallpaper`, patrón RAII `DesktopWallpaperSession`, apply.rs:908). Instanciar el enumerador de audio es el MISMO patrón. **Falta activar** la feature `Win32_Media_Audio` (+ `Win32_Devices_FunctionDiscovery`, `Win32_UI_Shell_PropertiesSystem`) en Cargo.toml — hoy ninguna feature de audio está activa. Molde de comando Tauri con doble rama `cfg`: displays_toggle (lib.rs:1284), displays_apply_layout (lib.rs:1472).
- **Gate local de compilación**: el crate scratch local (no versionado, `docs/DECISIONS.md:396`) espeja las features windows del proyecto e incluye los archivos reales por `#[path]` → sirve para chequear que el código COM/audio nuevo compila (`cargo check`, ambas ramas) antes de gastar CI. (Recordá: [[el-gate-local-de-compilacion-si-existe]].)

## Decisiones tomadas con Guido (entrevista 2026-07-24)
1. **Cómo se elige la salida de un perfil**: un **menú desplegable por perfil** ("Sonido a: …"), opt-in, con **"No tocar el audio" por defecto**. Se elige a mano; NO se captura al guardar.
2. **Auto-revert**: si un cambio de monitores se auto-revierte, **el audio también vuelve** a donde estaba (el perfil es una unidad).
3. **Salida no disponible** (TV apagada): **NO se cambia el audio y se avisa**; el video se aplica igual. **Sin vigilante de dispositivos** corriendo (no auto-switch cuando la TV se prende).

## AGREGA (lo nuevo)
- **Dato nuevo — `AudioTarget`**: `struct AudioTarget { endpoint_id: String, friendly_name: String }` (Serialize/Deserialize). `endpoint_id` = clave técnica opaca del endpoint (de `IMMDevice::GetId`); `friendly_name` = etiqueta linda para la UI y fallback si el id no resuelve.
- **Dato nuevo — el mapa por perfil**: `AppSettings.profile_audio: BTreeMap<String, AudioTarget>` (nombre_de_perfil → salida deseada), con `#[serde(default)]`. **Vive en `AppSettings`, NO en `Profile`** — mismo lugar y patrón que `profile_shortcuts`. Sin entrada = ese perfil está en "No tocar".
- **Backend — enumerar salidas**: comando Tauri nuevo `displays_list_audio_outputs` → `Vec<{ id, name }>` de las salidas de audio ACTIVAS. Usa `IMMDeviceEnumerator::EnumAudioEndpoints(eRender, DEVICE_STATE_ACTIVE)` + `GetId` + `PKEY_Device_FriendlyName` (**API documentada, ya presente en el crate `windows`** — sin trucos). Puebla el dropdown.
- **Backend — setear el default de Windows**: helper que cambia la salida por default a un `endpoint_id` **para los tres roles** (eConsole, eMultimedia, eCommunications) vía `IPolicyConfig::SetDefaultEndpoint`. Corre en `tokio::task::spawn_blocking` con COM inicializado en ese hilo (mismo molde RAII que `DesktopWallpaperSession`). Implementación: crate `com-policy-config` **o** la interfaz declarada a mano con la cascada de IIDs (ver Riesgos).
- **Backend — asignar/limpiar el audio de un perfil**: comandos `displays_set_profile_audio { name, endpointId, friendlyName }` y `displays_clear_profile_audio { name }` (molde exacto: `displays_set_profile_shortcut` / `displays_clear_profile_shortcut`). Escriben/borran la entrada en `profile_audio` y persisten displays.json.
- **Backend — captura/restore del audio en el rollback**: antes de aplicar el audio de un perfil que **sí** cambia el audio, capturar el default de audio ACTUAL **por rol** (`endpoint_id` **y** `friendly_name` de cada rol) y guardarlo como **estado paralelo en la capa `mod.rs`** — **NUNCA dentro de `PendingConfirmation`** (ese struct del vendor es intocable). Se setea al aplicar (solo si el perfil tenía salida asignada y disponible), se **limpia en `confirm`**, y se **consume en revert/timeout** para restaurar. Si el apply no cambió el audio, no hay nada capturado ni que restaurar. Al restaurar, mismo fallback por `friendly_name` que el camino de ida si el `endpoint_id` previo ya no resuelve.
- **Frontend — dropdown por perfil**: en cada item de PERFILES (`buildProfileItem`), un `<select>` "Sonido a: [No tocar | <dispositivos>]" con el estilo `displays-setting-select`. Se puebla con `displays_list_audio_outputs` + el `friendly_name` guardado del perfil; al cambiar invoca `displays_set_profile_audio` / `displays_clear_profile_audio`. Escapar los nombres con `setText`/`textContent` (vienen del sistema).
- **Frontend — aviso "salida no disponible"**: toast/evento cuando se aplica un perfil cuya salida de audio no está presente (TV apagada) o falló el cambio.

## MODIFICA (lo existente que se toca)
- **`AppSettings`** (`vendor/monarch/src/model.rs:99`): se agrega el campo `profile_audio`. → Un `displays.json` viejo (sin ese campo) DEBE seguir leyéndose igual — por eso `#[serde(default)]`; el resto de `AppSettings` queda intacto.
- **🔴 `update_settings`** (`vendor/monarch/src/manager.rs:404`, struct-literal ~línea 456): este método **NO copia el struct que recibe — lo re-arma campo por campo**. Es el embudo de TODOS los cambios de ajustes: `guardar_ajustes` (mod.rs:985, cambiar perfil de arranque / plazo / interruptor de atajos), `asignar_atajo`/`limpiar_atajo` (mod.rs:843/872) y `borrar_perfil` (mod.rs:818). → Al sumar `profile_audio` al struct, ese literal **deja de compilar**; DEBE completarse con `profile_audio: settings.profile_audio` (copiar tal cual del input). **NUNCA** con `Default::default()`, `..Default::default()` ni `BTreeMap::new()`: si se tapa así, **cada vez que Guido cambie el perfil de arranque, borre un perfil o toque un atajo se le vacían TODAS las asignaciones de audio, en silencio.** Esta es la trampa #1 de esta fase.
- **`cargar_perfil` / `aplicar_con_red`** (`mod.rs:889` / `mod.rs:1112`): tras aplicar el video, aplicar el audio del perfil (si tiene entrada y la salida está disponible) y capturar el audio previo para el rollback. → La red de auto-revert de **video** debe seguir andando **igual**; el audio es un paso adicional, best-effort. **OJO la rama no-op**: `cargar_perfil` tiene DOS ramas — si el perfil ya es el layout actual, cae en la rama `None` (mod.rs:900) que **no pasa por `aplicar_con_red`**. El audio DEBE aplicarse **también en esa rama** (caso: los monitores ya están puestos y solo falta mandar el sonido a la TV — el "botón único" solo-audio). Como esa rama no tiene cuenta regresiva, el audio se aplica y confirma directo (no hay rollback de audio ahí).
- **`aplicar_perfil_directo`** (`mod.rs:922`): misma lógica de audio para el **perfil de arranque** (lib.rs:2138) y los **atajos globales** (lib.rs:1276). → El commit inmediato del video NO cambia; el audio se aplica también por estas vías.
- **`rollback_pending` / `revert` / `reportar_desenlace`** (`manager.rs:179` / `mod.rs:706` / `mod.rs:1165`): al revertir el video, restaurar también el audio previo capturado (solo si este apply lo había cambiado). → El rollback de video (re-aplicar el layout) NO cambia de comportamiento; se le suma la restauración de audio desde el estado paralelo de `mod.rs`.
- **`confirm` / `confirm_current_layout`** (`mod.rs:694` / `manager.rs:168`): al confirmar el cambio, **descartar** el estado de "audio previo" capturado (ya no hay que revertir). → Sin esto, un audio-previo colgado podría restaurarse por error en un revert posterior de otro perfil. El `confirm_current_layout` del vendor NO cambia; la limpieza vive en la capa `mod.rs`.
- **`ProfileView` + `vista_de_perfil` + `listar_perfiles`** (`mod.rs:144` / `mod.rs:1242` / `mod.rs:788`): agregar a `ProfileView` un campo con la salida de audio guardada del perfil, cruzando `profile_audio` **igual que hoy `listar_perfiles` cruza `profile_shortcuts`** para el campo `shortcut`. → Sin esto, el dropdown se puebla con dispositivos pero arranca siempre en "No tocar" aunque el perfil tenga salida guardada, y Guido no ve lo que eligió.
- **Borrado de perfil** (`displays_delete_profile`, front main.js:2237 + su backend `borrar_perfil` mod.rs:818): al borrar un perfil, limpiar también su entrada en `profile_audio`. → Igual que hoy se limpia su atajo; no dejar entradas huérfanas. (Este borrado pasa por `update_settings` → ver la trampa #1.)
- **`Cargo.toml`**: activar las features `Win32_Media_Audio` (+ `Win32_Devices_FunctionDiscovery`, `Win32_UI_Shell_PropertiesSystem`) en la tabla `[target.'cfg(target_os="windows")'.dependencies]`, y sumar la dep `com-policy-config` (si se usa el crate). → NO cambiar el pin de `windows = "0.60"` ni las features ya activas; ojo alinear versiones (ver Riesgos).
- **El invoke_handler** (`lib.rs:2167`): sumar los 3 comandos nuevos a la lista `generate_handler![…]`. → Los ~44 comandos existentes quedan igual.

## NO SE TOCA (obligatoria — el seguro de no romper)
- **El struct `Profile`** (`model.rs:87`): **NO se le agrega ningún campo.** El audio vive aparte, en `AppSettings`. La topología de video del perfil queda idéntica byte a byte.
- **Los perfiles guardados del usuario** (`AppConfig.profiles`): ni se migran, ni se transforman, ni se renombran, ni se reordenan.
- **El motor CCD de video** (SetDisplayConfig/QueryDisplayConfig), la **red de auto-revert de video**, el lienzo, el primario, el perfil de arranque, los atajos y las resoluciones guardadas — intactos.
- **El núcleo de Millennium**: clipboard, discovery mDNS, servidor HTTPS/axum, transferencias, pinning de certificados — intacto. El formato del hello UDP y del JSON de `/info` — intacto.
- **El COM existente de `IDesktopWallpaper`** y su manejo de apartment (should_uninitialize): el audio usa su propio scope COM y NO le rompe el apartment al wallpaper.
- **El estilo neón** y el patrón push-based / diff incremental del frontend (`buildPeerItem`/`updatePeerItem`, y `buildProfileItem` por diff).
- **La regla de CPU en reposo ~0%**: el audio NO agrega timers ni polls (sin vigilante de dispositivos — decisión 3). En reposo, cero trabajo nuevo.
- **Android / no-Windows**: todo el código de audio va detrás de `#[cfg(target_os = "windows")]`; el dropdown de audio no se renderiza en `is-mobile`. El build de Android NO se rompe.

## Criterios de aceptación (verificables, regresión primero)
> **Vara de regresión**: el release actual **`v1.3.0`** (Displays v2 Fase 1+2).
1. **Regresión**: todo lo de NO SE TOCA sigue igual. En particular, un `displays.json` de v1.3.0 (sin datos de audio) DEBE abrir sin romper, con **todos los perfiles en "No tocar"** y sus monitores/atajos/primario/startup idénticos; el auto-revert de video, el lienzo y las transferencias del clipboard andan igual.
2. CUANDO Guido elige una salida de audio para un perfil, el sistema DEBE persistirla en `displays.json` (dentro de `profile_audio`) y DEBE reaparecer al reabrir la app. **Y esa asignación DEBE seguir intacta después de cambiar el perfil de arranque, borrar OTRO perfil, o tocar un atajo** (regresión de la trampa #1 — el bug de `update_settings`).
3. CUANDO aplica un perfil con salida asignada **y esa salida está disponible**, el default de Windows DEBE cambiar a esa salida **para los tres roles** — verificable en el panel de Sonido: tanto "Dispositivo predeterminado" como "Dispositivo de comunicación" apuntan a la salida del perfil. Esto DEBE pasar **aunque los monitores ya estuvieran en esa disposición** (video no-op): el audio igual cambia.
4. CUANDO aplica un perfil en "No tocar", el audio NO DEBE cambiar.
5. CUANDO un cambio de monitores se auto-revierte (por timeout **o** por REVERTIR manual), el audio DEBE volver a la salida que estaba **antes** de aplicar el perfil.
6. CUANDO aplica un perfil cuya salida NO está presente (TV apagada), el audio NO DEBE cambiar y la app DEBE avisar; el **video se aplica igual**.
7. El cambio de audio DEBE ocurrir también por las vías sin cuenta regresiva: **perfil de arranque** y **atajo global** de perfil.
8. En **Android / no-Windows** el build NO DEBE romperse y el dropdown de audio NO DEBE aparecer; y **CPU en reposo ~0%** (Task Manager) — el audio no agrega timers.

## Supuestos
- [ALTO] El audio se guarda **keyed por NOMBRE de perfil** (como los atajos). Si un perfil se "renombra" (hoy = borrar + recrear con otro nombre), el audio no se arrastra solo — misma limitación que los atajos. Aceptable.
- [ALTO] El audio es **best-effort**: si `SetDefaultEndpoint` falla (HRESULT de error) o la salida no está presente, el **video ya aplicado NO se revierte** por eso — se loguea (`runtime_log`) + avisa. (El audio no arrastra al video; el video **sí** arrastra al audio en el revert, por la decisión 2.)
- [MEDIO] Se setean los **3 roles** para que "todo el sonido" vaya a la salida; con uno solo no alcanza (verificado en el spike — apps de música/llamadas podrían quedar en la salida vieja).
- [MEDIO] `com-policy-config` pide `windows 0.61` y el proyecto fija `windows 0.60`. Si chocan (dos copias incompatibles de los tipos COM), se **declara `IPolicyConfig` a mano** (~100 líneas, con la cascada de IIDs) en vez de depender del crate. Se resuelve en el build; no bloquea el diseño.
- [BAJO] Se guardan `endpoint_id` (clave) + `friendly_name` (etiqueta + fallback). Si el `endpoint_id` no resuelve (cambio/reinstalación de driver, o USB sin serial a otro puerto), se intenta re-emparejar por `friendly_name`; si no hay match, el perfil queda "salida perdida" y **no re-rutea en silencio**.
- [BAJO] Sin auto-switch cuando la TV se prende (sin `IMMNotificationClient` corriendo) — decisión 3.

## Riesgos y decisiones ⚠️
- ⚠️ **`IPolicyConfig` es no documentado.** Es la ÚNICA vía nativa para SETEAR el default (confirmado: Microsoft no publica API para esto, solo para leer/enumerar). La usan el propio panel de Sonido de Windows + EarTrumpet / SoundVolumeView / NirCmd / AudioDeviceCmdlets desde hace ~15 años → riesgo real **bajo**, no cero. **Consecuencia** si un update de Windows la rompe: el audio deja de cambiar (falla silenciosa, HRESULT de error, el video no se afecta) → **Plan B: shell-out a NirCmd o `Set-AudioDevice` (PowerShell)**.
- ⚠️ **Variantes de IID por versión de Windows.** El `QueryInterface` del IID Win7+ (`f8679f50…`) falla en ALGUNOS builds de Win10; las tools serias prueban en cascada `IPolicyConfig → IPolicyConfigVista → IPolicyConfig10` (este último con el IID de `IUnknown`). **Decisión**: implementar la cascada en el build. En el Win11 de Guido el IID normal anda. **Consecuencia** si no se hace: podría fallar en máquinas con Win10 viejo.
- ⚠️ **Toca datos del usuario (`displays.json`) — DOS trampas de pérdida de datos.** Migración aditiva, tabla "esto cambio / esto preservo" arriba. **Trampa de LECTURA**: si por error se agregara el campo a `Profile` sin default, un `displays.json` viejo NO deserializaría → **se perderían TODOS los perfiles**. Por eso el audio va en `AppSettings` (que ya tiene `#[serde(default)]` de struct) y **NUNCA** en `Profile`. **Trampa de ESCRITURA (#1)**: `update_settings` re-arma los ajustes campo por campo; si no copia `profile_audio` del input, cada guardado de ajustes **borra todas las asignaciones de audio** (ver MODIFICA + criterio 2). Ambas son la clase de dato sagrado que la regla dura protege; el criterio 1 (regresión) y el 2 las blindan.
- ⚠️ **Rollback de audio (mecanismo nuevo).** Capturar el default previo (3 roles) antes de aplicar y restaurarlo en el revert. **Consecuencia** si falla: el sonido podría quedar en la TV con los monitores ya revertidos (molesto, no roto). **Verificar E2E** el caso de auto-revert con audio (regla de evidencia del proyecto: reproducir el caso, no "apliqué el parche").
- ⚠️ **Editar el crate vendorizado `monarch`.** El campo nuevo va en `AppSettings`, que vive en `vendor/monarch/src/model.rs` — y ya fue extendido antes (los shortcuts viven ahí). **Consecuencia**: se toca código vendorizado, pero es el patrón establecido; el **motor de video del vendor NO se toca**, solo el struct de settings.
